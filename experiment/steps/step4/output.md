
根据四个来源提供的信息，Agent 的属性可以按照它们所回答的维度进行以下分组。这些分组揭示了不同来源在定义 Agent 时关注点的差异（如 A2 侧重工程接口，A4 侧重通信协议，A1/A3 侧重系统能力）。

### 1. What is it?（本体与角色：它在性质上是什么？）

这一维度回答 Agent 的实体定义和在系统中扮演的基本身份。

* **自主的软件实体/系统（Autonomous Entity/System）：** 这是 Agent 的核心属性，强调其独立性。
* **特定角色（Role-playing）：** 强调 Agent 不是通用的问答机，而是为了履行特定职能而存在的。
* **配置了指令和工具的大语言模型（Configured LLM）：** 在 A2 的定义中，Agent 被直接等同于一种特定配置后的 LLM 实体。
* **名称（Name）：** Agent 在系统中的唯一标识符。
* **身份信息（Identity）：** 用于身份验证和问责的属性。

### 2. What does it do?（行为与功能：它能产生什么作用？）

这一维度关注 Agent 对外的表现及其完成任务的能力。

* **感知与行动（Perceive & Act）：** 所有的来源（直接或间接）都强调 Agent 必须能感知环境并执行动作以改变环境。
* **达成特定目标（Goal-oriented）：** 强调其行为是有目的性的，而非随机响应。
* **处理多步骤复杂任务（Multi-step tasks）：** 能够将复杂流程自动化，而非单次交互。
* **移交与协作（Handoffs/Collaboration）：** 能够将任务委托给其他 Agent 或进行对等协作。
* **自我演化（Self-evolution）：** 能够像人类一样从环境中学习并进化自身。

### 3. How does it operate?（运行机制：它如何进行内部运作？）

这一维度描述 Agent 内部处理信息和驱动决策的逻辑。

* **推理与规划（Reasoning & Planning）：** Agent 依据目标和上下文动态决定后续步骤，而非遵循固定脚本。
* **自适应性（Adaptability）：** 能够根据环境变化和新信息调整自己的策略。
* **维持内部状态/上下文（Internal State/Context）：** 记录对话历史、中间结果和任务状态，以保证行为的一致性。
* **持续性（Persistence）：** 代理的过程是随时间持续的，而非单次触发。
* **动态决策（Dynamic Decision Making）：** 在运行时实时决定调用哪些工具或协作对象。

### 4. How is it implemented?（实现方式：它由哪些技术组件构成？）

这一维度涉及构建 Agent 的具体“硬件基础”或软件资源。

* **核心控制器（AI Models/LLMs）：** 作为理解和推理的核心引擎。
* **四模块/部分架构（Profiling, Memory, Planning, Action）：** 来源提出的统一设计模式，包括记忆系统、执行框架等组件。
* **外部工具集成（Tools/APIs）：** 扩展其行动能力的外部插件或服务器（如 MCP 协议服务器）。
* **提示工程与微调（Prompts/Fine-tuning）：** 获取和调整 Agent 能力的技术手段。
* **编排框架（Orchestration frameworks）：** 用于协调各组件运作的支撑系统。

### 5. How is it exposed & governed?（接口与治理：它如何被外界访问和约束？）

这一维度关注 Agent 的边界规范、安全合规及商业管理。

* **身份验证与协议（Authentication/Protocols）：** 规定通信双方必须进行相互认证，并遵循加密等网络协议。
* **结构化输出（Structured Output）：** 规定 Agent 必须产生特定格式（如 Pydantic 对象）的结果。
* **护栏与生命周期回调（Guardrails/Hooks）：** 对输出进行过滤验证，或通过回调函数观察其生命周期。
* **人类监督与治理（Human oversight）：** 强调在部署时必须具备透明度和人类监管。
* **商业价值（Business value）：** 从企业角度衡量 Agent 的产出效率。

---

### 特别识别：属于多个维度的属性

* **大语言模型 (LLM/AI Models)：**
  * **属于【实现方式】：** 它是构建当代 Agent 的关键技术手段。
  * **属于【本体角色】：** 在某些视角下，Agent 被直接定义为 LLM 的一种特定配置形态。
* **工具调用 (Tools)：**
  * **属于【行为功能】：** 它定义了 Agent 能够“做”什么的边界。
  * **属于【实现方式】：** 它表现为 API 集成或特定的工具服务器配置。
* **身份与名称 (Identity/Name)：**
  * **属于【本体角色】：** 它是定义“这是一个谁”的基本元数据。
  * **属于【接口治理】：** 它是网络协议中进行安全验证和问责的必需字段。
* **记忆与状态 (Memory/Internal State)：**
  * **属于【运行机制】：** 它是实现推理连贯性和持续性的逻辑基础。
  * **属于【实现方式】：** 它通常由向量数据库、应用层缓存或特定的记忆模块结构来实现。

### 无法合理归类的属性

* **不透明性（Opaqueness）：** A4 提到 Agent 之间可能对彼此保持不透明，仅通过接口协作。这既不完全是能力，也不完全是实现，而是一种**架构设计原则**。
* **类人智能（Human-like Intelligence）：** A1 提到的一种预期目标。这更像是一种**愿景描述**，而非具体属性。
